## 经核实的接口选择

根路径：`https://bbs-api.miyoushe.com/community/ugc_community/web/api`

| 用途 | 请求 | 起始排序 |
| --- | --- | --- |
| 关卡详情 | GET `/level/detail?level_id=...&uid=&region=cn_gf01&lang=zh-cn` | 无 |
| 增量主评论 | POST `/reply/list?lang=zh-cn` | `SORT_TYPE_FLOOR_DESC` |
| 全量主评论 | 同上 | `SORT_TYPE_HOT` |
| 楼中楼 | POST `/level/reply/sub_replies?lang=zh-cn`，额外带 `parent_reply_id` | `SORT_TYPE_FLOOR_ASC` |

请求保持 `uid: ""`，不发送账号 cookie、Authorization 或登录凭据。通过 Core 原有 `network.public` 能力、原有主机白名单访问；未新增登录或站外主机权限。

当前没有核实到独立按时间排序、按编辑时间查询或变更流接口。楼层降序在样本上与创建时间降序相符，但不能把它说成服务端时间游标。楼中楼 DESC 存在实际游标排序切换，ASC 的 41 条样本完整遍历已验证。更完整的来源、游标实测与边界见 `API-RESEARCH.md` 和不含评论正文/用户资料的 `api-probe-evidence.json`。

## 默认配置与范围

0.1.2 界面分为“评论采集”和“评论监测”子页签。在采集入口输入关卡 ID 完成采集，再在结果页点击“添加监测”；监测页显示目标、运行状态、暂停/恢复与评论入口。首次添加目标自动启用，向已有暂停列表添加保持暂停；移除目标会停止对应任务，但保留归档与状态。高级设置入口位于暂停/恢复旁边，通过右侧 Sidebar 展示；增量和全量周期以分钟输入，保存时兼容原有秒值。已有配置保留，新配置默认每 30 分钟增量。卡片显示下一次调度时间，包含失败冷却；暂停/采集中不显示无效时间。保存中禁用重复提交，成功持续显示已保存/设置已生效，失败保留草稿并提示原因。卡片的指标为一行，最近新增分为推荐/不推荐，按最近一轮新增主评论统计，不计已有修改及楼中楼。结果页直接浏览最新累计归档。隐藏监测页时不轮询状态，返回时刷新。

| 字段 | 默认 | 范围 / 语义 |
| --- | --- | --- |
| enabled | false | 必须在界面主动启用 |
| level_ids | [] | 1–20 位纯数字字符串，去重，最多 100 个；ID 不转为 JavaScript 数字 |
| incremental_interval_secs | 1800 | 60–86400 秒 |
| full_interval_secs | 86400 | 300–2592000 秒，不能小于增量周期 |
| max_parallel | 2 | 1–4，前台手动采集与后台合计的采集任务上限 |
| request_interval_ms | 500 | 250–60000ms，所有关卡/接口/重试共享 |
| overlap_pages | 2 | 1–10 个连续“全部主评论均已知”的重叠页 |
| incremental_max_pages | 50 | 1–500 主评论页，且不能小于 overlap_pages |

全量上限：主评论最多 500 页；每个楼中楼线程最多 500 页；一轮合计最多 20000 个评论页请求。详情与失败重试不计页数。上限是安全中止条件，达到时明确记录 partial，不宣称完成。线程很多或数据量很大的关卡可能需要以后增加分片/可恢复深度扫描；本次不擅自合成游标跨进程续抓。

## 增量与完整性语义

- 每轮从空游标开始，保留服务器不透明游标，不按楼层、时间或 next 自行加减
- 每页补回服务端返回游标中省略的 size；排序改变会报错，绝不混用两种排序的游标
- 主评论按 ID 去重；连续已知页达到 overlap_pages 才结束增量，不以单条旧 ID 或创建时间截止
- 增量停点取自只在成功后提交的独立 frontier；中断/失败保存到归档的新评论不会污染停点，因此重试不会因“前几页已经见过”而跳过尚未抓到的积压
- 失败后下一轮在指数冷却后优先全量恢复；不把增量页数上限当成“已追上”
- 每个访问到的有回复主楼单独遍历楼中楼 ASC；实际返回数少于主楼声明数时继续其他楼层，但整轮标 partial
- 缺少/重复游标、整页重复、异常排序、空页却有下一页、损坏结构、网络失败、取消和页数上限均不能产生成功全量标记
- 本轮接口未出现的评论仍留在累计归档里，不据此认定删除
- “完整”表示本次选择范围的接口遍历完成。接口是可变的公开窗口，不是事务性快照；分页期间的热度变化、审核、隐藏、删除或新评论可能改变结果，无法保证抓到站方未提供的数据
- 增量只刷新最新窗口及其楼中楼。旧楼的新回复、旧正文/昵称/点赞数等变化需要长周期全量补查

## 并发、失败与重启

同一关卡的前台/后台采集互斥，不同关卡可并行。任务上限包含手动采集，排队冲突不累计网络失败。请求开始时间由唯一限速器控制，不是每个 worker 各自限速。停止时限速队列会检查取消；在途请求最多等 Core 返回/超时后结束。

网络超时、连接错误，以及可识别的 HTTP 429/500/502/503/504 最多再试 2 次。429 退避也施加到全局限速器。Core 0.1.8 对部分 HTTP 错误不提供状态码：这种错误不会被伪装成 500 或盲目重试，后续由调度冷却处理。业务错误、登录/权限问题和结构错误不做短重试。

失败调度冷却为增量间隔乘以 `2^min(连续失败数,6)`，最多 24 小时。全量完成时间单独记录，失败和增量不会把长周期推迟。后台 panic 由监督任务处理，释放状态/槽位；不会永久卡在“运行中”。暂停未完成的全量任务会持久化需要全量恢复的标记；重新启用或重启后优先全量，只有成功全量才清除此标记，不增加网络失败计数。

SDK `serve_with_startup` 在 Core 握手后恢复后台调度；后台使用稳定的启动 HostClient，不继承偶然的跨插件调用上下文。Core 关闭/禁用插件/系统休眠时不运行。重启不会堆积执行所有错过的时刻，每个关卡只重新判定当前到期任务；无成功基线时先全量。

## 数据与磁盘容量

Core 原数据根目录中的 `archive-v1/` 保持不变，累计归档使用 v3 格式，读取时兼容 v1/v2 且不改写旧文件：

- `<level_id>.json`：最新累计归档
- `frontiers/<level_id>.json`：只在成功扫描后提交的主评论 ID 停点集合
- `monitor-config.json`：监测设置
- `monitor-state.json`：各关卡尝试/成功/全量时间与失败状态
- `recovery/`：重新采集前保留的损坏或不兼容原归档

每个关卡只维护一份最新累计归档，其中 `last_new_counts` 保存最近一轮新增主评论的推荐/不推荐数。未知推荐状态、楼中楼和旧评论修改不计入；本轮新增为零时覆盖为零。失败或取消后也保存已观察到的新评论统计。旧归档无该字段时返回 null，界面显示“—”，不扫描遗留文件推算。

每约 10 页写当前归档检查点，中断时保留已抓取数据。临时文件先同步落盘再替换目标；不跨进程复用网络游标。已移除历史版本浏览和对应接口，采集不再生成归档副本；已有旧文件不删除。JSON/CSV/Excel 导出仍导出最新累计归档。

插件需要 Core 0.1.8 源码和相对路径 SDK；不能把它当成完全独立 npm/Rust 项目构建。

```powershell

# Core 工作目录
# 将交付的 source/comment_collector 放到 Core/plugins/comment_collector
cd plugins/comment_collector

cargo fmt --all -- --check
cargo clippy --all-targets --all-features --locked -- -D warnings

cargo run --locked --features bindings --example generate_bindings -- --check

pnpm --dir ui run build
```

## Windows 上建议验收

1. Debug Core 安装 Debug 目录包，确认已有 v1/v2/v3 归档能打开，旧导出/收藏仍正常
2. 启用两个公开关卡，观察首次全量和后续增量，不超过全局请求速率
3. 前台采集与监测同一关卡，确认提示忙而不覆盖归档；不同关卡不超过并行上限
4. 关闭监测、移除关卡、取消前台采集，确认已抓取数据和 partial 状态保留
5. 退出 Core 再启动，确认配置恢复、没有“永远运行中”，不并发重放漏掉的周期
6. 检查最近新增推荐/不推荐数，重启后仍可读；重复采集不会重复计数，模拟失败不会显示全量成功
7. 确认磁盘容量，再选择长期周期

真实 Windows Core GUI、长时间运行、机器睡眠/唤醒、Windows 原子替换与 .wplug 安装仍需目标环境验收。不要把 Linux 单元/协议测试和公开 HTTP 小样本调查当成这些验收已完成。
